Design notes worth flagging for the next agent:

  - **Invalid-state actions are no-ops, not throws**. Implementation is
    `set((s) => s.phase === EXPECTED ? { ... } : {})`. Reasoning: the UI
    only exposes an action's button while in the corresponding phase, so
    in practice the wrong-phase path is dead. Choosing no-op over throw
    means a hot-reload, double-click, or stale-closure dispatch can't crash
    the app. If T5+ ever needs to *detect* an invalid dispatch (e.g. for
    logging), revisit — the cheapest path is to switch to throws and let
    the call sites catch.
  - **Test reset uses merge, not replace**. `useGameStore.setState({
    ...INITIAL_STATE })` (no `true` second arg). The replace mode wipes the
    action functions off the store, breaking subsequent action calls in
    the same test. This is documented in zustand but is a foot-gun on
    first encounter. INITIAL_STATE is exported for this exact use.
  - **PermissionPhase calls getUserMedia and immediately stops the tracks**.
    Why: the only goal of this phase is to surface the browser permission
    prompt. The actual recording stream is requested again by the recorder
    wrapper inside RecordingAPhase. After permission is granted, the
    second getUserMedia call resolves silently with no prompt. This avoids
    keeping a hot mic open across the HandoffA screen. Confirmed in iOS
    Safari and Chrome behavior docs; not e2e-tested (anti-goal).
  - **AudioContext is owned by App, passed as a factory**. Same pattern as
    pre-T4. RecordingAPhase takes `audioContextFactory: () => AudioContext`
    and forwards it to AudioRecorder. If T5 needs the same context in
    GuessingPhase (likely — both AudioRecorder and AudioPlayer want it),
    the right move is to extract a `useAudioContext` hook or stash it in
    the store. Don't create two contexts — most browsers cap them.
  - **Phase components dispatch via the store, not props**. They call
    `useGameStore((s) => s.action)` directly. This makes them harder to
    unit-test in isolation, but the store is itself well-tested and easy
    to seed via setState — net positive ergonomics. The same convention
    should hold for T5's HandoffB / Guessing / ConfirmEnd phases.
  - **DonePhase is throw-away**. It exists only so the T4 loop closes and
    a user doesn't get stuck. T5 (issue #6) replaces it with HandoffBPhase
    and the `done` value drops out of the Phase union. Don't add features
    here.
  - **Zustand v5 added** (`bun add zustand` → 5.0.12). PROJECT.md §4 lists
    zustand without a version; no surprise.
  - **Pre-commit gate verification skipped** in this session — I ran the
    individual scripts (typecheck/test/lint/format:check/build) but not
    `husky` itself. The hook should still fire on commit; if it fails
    because of staged-only oxfmt issues, run `bun run format` and re-stage.

Design notes worth flagging for the next agent:

  - **Why a Zustand store and not a React context**: the AC mentioned both as
    valid options. Picked Zustand because (a) the codebase already uses it
    for gameStore — same mental model, no new primitive, (b) testing pattern
    is identical (`setState` in `beforeEach`), (c) we can reset between
    tests via INITIAL_PLAYBACK_STATE without an explicit Provider wrapper
    in tests, (d) AudioPlayer can `useId()` for a per-instance id without
    needing the parent to thread one through.
  - **`useId` for the player id**: each `<AudioPlayer />` calls `useId()`
    once and uses it as its identity in the playback store. Stable across
    re-renders, unique per instance. No need for callers to pass an `id`
    prop — keeps the API surface unchanged.
  - **Order of effects matters here**. When the user clicks play:
    `handleToggle` sets local `isPlaying=true`, calls `setPlaying(myId)`,
    then `onPlay?.()`. The `useEffect` watching currentPlayingId then
    re-runs in every other AudioPlayer instance: if they're playing AND
    the new id isn't theirs, they pause themselves. The own-instance also
    re-runs but hits the `currentPlayingId !== playerId` guard and no-ops.
    This is intentional and load-bearing — don't reorder.
  - **`clearPlaying` is conditional on id match**. Reason: imagine A plays,
    then B plays (which auto-preempts A and sets currentPlayingId=B). Some
    millis later, A's `useEffect` runs, calls `playerRef.pause()` and sets
    local isPlaying=false. If we *also* called clearPlaying(A) at that
    point, it would no-op because currentPlayingId is already B — but
    semantically we don't need it anyway. The conditional clear in the
    store is the safety net for any "late pause" race.
  - **No coordination for the `setRate` / `setDirection` controls**. The
    coordination only fires on play/pause; speed/direction changes on a
    paused player don't disturb the active one. This matches the AC
    ("démarrer la lecture sur un AudioPlayer met en pause les autres").
  - **Test isolation note**: the `usePlaybackStore` is module-scoped global
    state. Vitest runs each test file in its own module instance (default
    `isolate: true`), so cross-file state doesn't leak. Within a file, the
    `beforeEach` reset is required — without it, a previous test's
    leftover `currentPlayingId` could trigger spurious auto-pauses on the
    next test's mount. Apply the same reset in any future test file that
    renders AudioPlayer.
  - **No new dependencies**. Zustand was already installed since T4.
  - **Coverage tool still not wired**. playbackStore is at 100% by
    inspection (every action + initial state covered).

2026-05-02 — Issue #20 (bug: audio dies after lock screen / app switch on iOS)

Added `src/audio/audioContextResume.ts` and wired it from `App.tsx` to
recover audio playback after the page returns from background. This is
the iOS-specific failure mode that was defeating the IndexedDB persistence
shipped earlier — the round survived the lock screen but the audio engine
did not.

Root cause analysis
   Two distinct quirks fire when an iOS PWA backgrounds for more than a
   few seconds:
     1. AudioContext.state moves to "suspended". Calling resume() outside
        a user gesture is a no-op on iOS, so the existing fire-and-forget
        `void audioContext.resume()` inside player.startSource() couldn't
        rescue the context once the user came back from lock screen and
        tapped a play button — the resume() call was actually inside a
        gesture (good) but the AVAudioSession category had also drifted
        (bad), so even the resumed context produced silent output.
     2. AVAudioSession category drifts back to "ambient" / "ringer" while
        the page is hidden. The well-known fix (already used at first-load
        in iosAudioUnlock.ts) is to play a short silent <audio> element
        through HTMLAudioElement, which forces the category back to
        "playback". This needs to be re-triggered on every wake-up cycle,
        not just at first-load.

Fix
   `installAudioContextResume(getContext, options)` listens to:
     - `visibilitychange` (when document.visibilityState becomes "visible")
     - `pageshow` with `persisted=true` (bfcache restore)

   On every "page is visible again" transition where the AudioContext is
   suspended, it:
     (a) calls `ctx.resume()` immediately — works on Chrome/Firefox where
         resume() is allowed without a user gesture, no-op on iOS;
     (b) arms a one-shot listener on pointerdown/touchstart/keydown that
         re-runs `ctx.resume()` from inside a user-gesture context AND (on
         iOS only) replays the silent WAV to re-prime AVAudioSession.

   The user's first interaction after wake-up — typically tapping a
   play button — is the trigger. Because the gesture handler is on
   `document` (bubble phase) and runs on pointerdown while the play
   button's onClick is on click, our recovery code fires BEFORE
   player.play() runs in the same gesture. Combined with the existing
   resume-from-startSource code path, the click-to-play sequence sees a
   running context with the right audio category.

Wiring
   `App.tsx`: added a second `useEffect` after the existing
   `installIosAudioUnlock` one, passing `() => audioContextRef.current`
   so the resume handler reads the lazily-created context without
   forcing it into existence (the context is still created on first
   `getAudioContext()` call from a phase that needs audio).

Tests
   `audioContextResume.test.ts` covers:
     - no-op when context not yet created / already running / page hidden
     - immediate resume() on visibilitychange (suspended + visible)
     - gesture-armed resume() and silent-WAV replay (iOS path)
     - non-iOS path skips the silent WAV
     - one-shot semantics (gesture fires only once per wake-up)
     - re-arming works across multiple background → foreground cycles
     - pageshow handling (persisted=true triggers; persisted=false ignored)
     - cleanup() removes both visibility and gesture listeners
     - resume() and play() rejections are swallowed (no throw)

   The iOS detection is injected via `isIos` option for deterministic
   tests; the user-agent check defaults via `isIosAudioCategoryQuirky()`
   from iosAudioUnlock.ts.

Verification
   - bun run typecheck → clean (the pre-existing `@cloudflare/vite-plugin`
     error went away after `bun install` — the package was in
     package.json but missing from node_modules)
   - bun run lint → 0 warnings, 0 errors (95 rules, 46 files)
   - bun run format:check → clean (47 files)
   - bun run test → 169/169 passing across 21 files

What is NOT in this PR (deliberately)
   - No UI message for the "context can't resume" edge case mentioned in
     issue #20's acceptance criteria. The two-pronged recovery (immediate
     resume + gesture-armed re-prime) should handle the failure modes
     observed in practice; if HITL testing on a real iPhone reveals a

Notes for next agent
   - `installAudioContextResume` deliberately does NOT force-create the
     AudioContext. The getter pattern (`() => audioContextRef.current`)

   - The silent WAV constant is duplicated between iosAudioUnlock.ts and

     drifts AVAudioSession after some minutes in background) and cannot

2026-05-02 — issue #21 — auto-scaling de la waveform d'enregistrement

Picked #21 because it was the highest-priority unblocked, non-HITL issue:
a real usability fix that affects every recording (quiet voices were
producing near-invisible bars), with a naturally testable pure
function. #22 (rename A/B → 1/2) and #23 (modal confirmation) were
also unblocked but felt lower-impact / required design decisions.

Approach
   The fixed VIZ_GAIN = 2.5 multiplier was the root cause: amplifying a
   raw RMS value by a constant means quiet voices that peak around
   RMS=0.05 only reach 12.5% bar height, while loud voices that hit
   RMS=0.5 saturate at 125% (clipped to 100%) for most of the
   recording. Either way the visible signal carries no information
   about the dynamic range within the take.

   Replaced with a rolling adaptive peak that's tracked frame-by-frame
   and used to normalize the bar heights at draw time. Loudest moment
   of the current take maps to ~80% of bar height regardless of
   absolute volume.

New module: src/audio/waveformScale.ts
   Three pure functions:
     - initialWaveformScaleState({ floorPeak? }) → { peak }
     - nextWaveformScaleState(state, instantRms, options?) → { peak }
       attack/release smoothing on the tracked peak. Attack 0.15
       (rises modestly toward new highs), release 0.003 (decays very
       slowly when input drops — keeps the scale stable across short
       silences). Clamped at floor 0.02 so noise floor doesn't get
       amplified.
     - rmsToBarHeight(rms, state, options?) → number in [0, 1]
       Divides rms by tracked peak, multiplies by targetFraction
       (default 0.75). Caps at maxHeight, floors at minHeight.

   All three are deterministic and side-effect-free. Tests cover:
   floor clamp, attack/release math, smooth multi-frame ramp, no
   flicker on small input fluctuations, equal visual range for quiet
   and loud voices at their respective peaks, edge cases (zero rms,
   tiny rms, rms above peak).

Wiring in AudioRecorder.tsx
   - VIZ_GAIN constant removed; VIZ_TARGET_FRACTION = 0.8 added (the
     loudest moment shows at 80% of bar height — leaves visual
     headroom so the user can see when they're "loud").
   - VIZ_MIN_BAR_PERCENT = 8 (replaces the literal 8 used in three
     places — initial JSX height, cleanup reset, and the previous
     min-height clamp).
   - Each frame: update scaleState, accumulate bucket RMS as before,
     then re-render ALL bars from index 0 to highestBucketDrawn using
     the current scale. This means previously-drawn bars rescale
     downward as the user gets louder — visually consistent with the
     "the loudest moment in this take is the reference" model. The
     stored bucket RMS values are unchanged; only the rendered height
     is recomputed.
   - Audio recording itself is unaffected — no change to
     MediaRecorder, no change to the AudioBuffer or Blob that's
     persisted/decoded/reversed/passed to onRecorded.

Acceptance criteria check
   - [x] Voix faible → bars remplissent ~50–80% de la hauteur sur les
         pics: yes (targetFraction = 0.8, floorPeak = 0.02 means even a
         quiet 0.02 RMS will scale to 0.8 / 0.02 * 0.02 = 80% at the
         personal peak).
   - [x] Voix forte → barres ne saturent pas constamment: yes
         (targetFraction = 0.8 leaves 20% headroom; only frames that
         exceed the tracked peak briefly clip at 100%, and the peak
         catches up via attack within a few frames).
   - [x] Échelle s'adapte progressivement (pas de flicker): attack 0.15
         and release 0.003 verified by test
         (does_not_flicker_when_input_alternates_around_the_current_peak).
   - [x] Aucune modif de l'AudioBuffer / Blob: confirmed — pure visual
         transform, reads bucket RMS but never mutates it for storage.
   - [x] Tests unitaires sur la fonction de scaling (pure): 11 tests
         in waveformScale.test.ts.

Verification
   - bun run typecheck → clean
   - bun run lint → 0 warnings, 0 errors (95 rules, 48 files)
   - bun run format:check → clean (49 files)
   - bun run test → 180/180 passing across 22 test files (was 169
     across 21 — added 11 tests in 1 new file, all green)

Notes for next agent
   - The tuning constants (attack 0.15, release 0.003,
     targetFraction 0.8, floorPeak 0.02) are conservative starting
     points. If HITL on a real device shows the bars feeling too
     "settled" or too "twitchy", these are the levers — change them
     in waveformScale.ts (defaults) or pass options at the call site
     in AudioRecorder.tsx. The pure-function tests don't pin specific
     values for the defaults, so they tolerate tuning.
   - The render loop now redraws every active bar each frame instead

     negligible (~3840 style writes/sec at the worst case, near the

2026-05-02 — Issue #28 (Mode Challenge — règle : timer pour le devineur)

Closes the third v0.2 rule slice. The timer rule is now applied
during the guessing phase: when challengeRules.timerMs is non-null,
a wall-clock countdown ticks every 250 ms, displays as "Temps : m:ss"
above the original-recording card, and forces a transition to reveal
when it hits zero (skipping confirmEnd, per §3.12 line 211). The
countdown survives a lock-screen / PWA unload via guessingStartedAt
(epoch ms) which is persisted alongside the rest of the round; on
rehydration, if (Date.now() - guessingStartedAt) >= timerMs, App
jumps straight to reveal.

Persistence schema decision
   - Followed the pattern set by #29/#30 (challengeRules): added
     guessingStartedAt as an OPTIONAL field at the read site
     (guessingStartedAt?: ... in RawState; raw.guessingStartedAt
     ?? null on load). No version bump. A pre-timer save just loads
     with guessingStartedAt: null, and Mode 1 saves never set it
     anyway (timerMs gates the assignment).
   - Documented compatibility with two new persistence tests:
     "round-trips guessingStartedAt" + "loads guessingStartedAt as
     null when absent from a pre-timer save".

Store changes (src/store/gameStore.ts)
   - GameState: + guessingStartedAt: number | null
   - INITIAL_STATE: + guessingStartedAt: null
   - finishRecordingA: writes guessingStartedAt = Date.now() iff
     challengeRules?.timerMs != null. Mode 1 leaves it null.
   - confirmEnd / newRound: clear guessingStartedAt (null).
   - NEW action forceReveal(): guessing | confirmEnd → reveal,
     clears guessingStartedAt. Used by the timer hook.
   - cancelEnd does NOT touch guessingStartedAt — wall-clock keeps
     ticking through confirmEnd ↔ guessing toggles, per §3.12 line
     212 ("timer ne pause pas pendant les ré-écoutes").

Hook (src/phases/useGuessingTimer.ts — new file)
   - Reads challengeRules.timerMs, guessingStartedAt, phase from
     the store; injectable now() for deterministic tests.
   - setInterval(250 ms) tick recomputes remaining = timerMs -
     (now - startedAt). On <= 0, dispatches forceReveal() and lets
     the cleanup tear down the interval.
   - Active iff timerMs !== null && startedAt !== null && phase ∈
     {guessing, confirmEnd}. Returns { remainingMs: number | null }.
   - formatRemaining(ms) → "m:ss" with ceil-on-seconds rounding.

GuessingPhase (src/phases/GuessingPhase.tsx)
   - Calls useGuessingTimer() at top-level (above the originalRecording
     null guard, so hook order stays stable).
   - Renders <p aria-label="Temps restant" aria-live="polite"> only
     when remainingMs !== null. Sits between the h2 and the original
     player card.

App.tsx hydration
   - Computes `expired = timerMs !== null && startedAt !== null &&
     phase ∈ {guessing, confirmEnd} && Date.now() - startedAt >= timerMs`
     before setState. If expired: jump straight to "reveal" with
     guessingStartedAt cleared. Otherwise restore as-is.

"Ouzbek Challenge" → écran de config (timer + ré-écoutes,
notes intentionnellement absente) → flow Ouzbek 4-joueurs
avec règles appliquées à guessingP2 ET guessingP4.

Décisions de triage prises au démarrage (issue les listait
"à confirmer pendant la triage") :

 - Notes activées/désactivées : retirée de la config Ouzbek.
   Pourquoi : la note de J2 est le pivot du jeu ; J3 enregistre
   en lisant cette note ; la désactiver casserait la chaîne.
   Décision = forcer notesEnabled=true en interne (le chip
   "Désactivées" n'est pas rendu plutôt que grisé — code mort
   évité).
 - Timer : appliqué à guessingP2 ET guessingP4 (pas seulement
   au devineur final). Pourquoi : le timer crée la même tension
   pour le devineur (P4) que pour le transcripteur (P2). La
   note partielle est conservée au timeout.
 - Ré-écoutes : appliqué à guessingP2 ET guessingP4 (un seul
   listenCount partagé qui se reset à finishGuessingP2, suivant
   la reco PROJECT.md §3.13). P2 et P4 partent chacun avec une
   fresh budget = listenLimit.
 - Timer expiry behavior par phase :
     guessingP2 timeout → handoffP3 (la chaîne avance avec la
       note partielle, fidèle à l'esprit "Ouzbek") ;
     guessingP4 timeout → revealOuzbek (game over, comme
       Mode 1 timeout = reveal direct).
