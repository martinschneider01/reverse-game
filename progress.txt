app records mic input, decodes the WebM/Opus blob to an AudioBuffer, and plays

oxlint, oxfmt --check, vite build incl. PWA SW).

Modules delivered:
  - src/audio/decodeRecording.ts (+ .test.ts) — pure async fn,
    Blob → ArrayBuffer → AudioBuffer via injected AudioContext.decodeAudioData.
    5 tests, all paths covered (mono/stereo, decode failure, blob.arrayBuffer
    failure short-circuits before decodeAudioData).

    createRecorder({ maxDurationMs }) → { start, stop, cancel }. Wraps
    getUserMedia + MediaRecorder, enforces maxDurationMs via setTimeout that
    triggers requestStop, stops all stream tracks on finalize. 10 tests with
    fake MediaRecorder + getUserMedia stubs.
  - src/audio/wrappers/player.ts (+ .test.ts) — factory
    createPlayer(ctx) → { load, play, pause, onEnded }. Recreates an
    AudioBufferSourceNode per play() (one-shot lifecycle), disposes on
    pause/replay, only fires onEnded when the source ended naturally (not on
    manual pause). Resumes the AudioContext if suspended. 9 tests.
  - src/components/AudioRecorder.tsx (+ .test.tsx) — UI: Enregistrer / Arrêter
    buttons, Décodage state, error + Réessayer on permission denial. Uses
    injected recorderFactory / audioContextFactory / decode for testability.
  - src/components/AudioPlayer.tsx (+ .test.tsx) — minimal play/pause toggle,
    auto-resets to "Lecture" label when the player reports end-of-buffer.

Design notes worth flagging for the next agent:

  - **Wrapper injection convention**: components accept `recorderFactory` /
    `playerFactory` / `audioContextFactory` props with browser-API defaults.
    Tests pass fakes; production wires up real APIs. Phase components in T4+
    should follow the same convention so we never need a real AudioContext in
    jsdom.
  - **AudioRecorder emits AudioBuffer (not Recording)**: per T2 acceptance
    criteria. T3 (issue #4) will (a) add reverseBuffer, (b) change the
    AudioRecorder callback to emit a `Recording = { forward, reverse,
    durationMs }`, (c) extend the player wrapper with setRate/setDirection,
    and (d) add a slider + direction toggle to AudioPlayer. Plan to keep the
    AudioRecorder API change in one commit to avoid two passes through the
    component tests.
  - **AudioContext lifecycle in App**: App.tsx lazily creates a single
    AudioContext via a ref (audioContextRef) and shares it between the
    recorder's decode step and the player. This matters because most browsers
    cap the number of contexts. T4 should likely move this into a small
    `useAudioContext` hook or the Zustand store once more components need it.
  - **MediaRecorder mimeType**: we read `mediaRecorder.mimeType` and fall back
    to "audio/webm" if empty (jsdom returns empty). Real browsers will return
    a usable type; iOS Safari returns "audio/mp4". decodeAudioData handles
    both, but note this if we ever want to inspect the container.
  - **Recorder state machine**: a Session has an `active` flag; once
    auto-stop or manual stop has finalized, `active` flips false but the
    Session lingers so a late `stop()` call can still await the cached
    finalize promise. start() can replace a finalized session. cancel() nulls
    the session and suppresses the finalize resolution. The "active" flag is
    the one place to look if behavior here gets weird.
  - **No coverage tool wired into the gate** (yet). The 100% claim for
    decodeRecording/reverseBuffer per PROJECT.md §8 is by inspection, not
    enforced. T3 might be a good moment to add `bun run coverage` if we want
    a CI-like signal locally.
  - **@testing-library/user-event added** as a devDep — needed for click /
    type interactions in RTL tests. Standard companion to RTL, no surprise.
  - **`.gitkeep` placeholders removed** from src/audio, src/audio/wrappers,
    src/components now that those dirs have real files. src/phases and
    src/store still hold .gitkeep — they'll be populated in T4.

plays forward → toggles reverse → varies speed (0.25–2× with snap on 1×). All

Modules delivered:

  - src/audio/reverseBuffer.ts (+ .test.ts) — pure fn `(AudioBuffer, factory)
    => AudioBuffer`. The factory is either a `(channels, length, sampleRate)
    => AudioBuffer` callback (used in tests) or an `AudioContext` whose
    `createBuffer` is invoked. 7 tests: mono/stereo/odd-length/single-sample,
    sample-rate + channel count + length preserved, source not mutated,
    AudioContext path. Per-channel reverse via index walk on a fresh
    Float32Array allocated by the factory — source channel data is read but
    never mutated.

      • `load(Recording)` (was `load(AudioBuffer)`)
      • `setRate(rate)` — applied to live source's `playbackRate.value` if
        playing; otherwise stored for the next play().
      • `setDirection('forward'|'reverse')` — if not playing, just stores it;
        if playing AND the new direction differs, disposes the current source
        and re-starts a new one with the other buffer (rate preserved). The
        same-direction case is a no-op.

    no-op, rate preserved across direction swap, no spurious onEnded fired
    when setDirection replaces the source mid-playback.

    `Recording`. Computes both buffers via injected `decode` then `reverse`,
    derives `durationMs` as `forward.length / forward.sampleRate * 1000`.
    Test updated; new `reverse` prop wired with the same factory-injection
    convention as `decode`/`recorderFactory`.
  - src/components/AudioPlayer.tsx — props changed: takes a `recording` (was
    `buffer`) plus an optional `initialDirection`. UI now renders:
      • play/pause toggle (existing)
      • a "Sens : à l'endroit / à l'envers" toggle button
      • a `<input type="range">` 0.25–2.0 step 0.01 with `aria-label="Vitesse"`,

Design notes worth flagging for the next agent:

  - **Why factory injection for reverseBuffer**: the function needs to allocate
    a fresh AudioBuffer. In jsdom there is no AudioContext, so the test passes
    a `(channels, length, sampleRate) => AudioBuffer` factory directly.
    Production code passes an AudioContext (the function detects it by
    `typeof factory === "function"` vs object) and calls `ctx.createBuffer`.
    Keeps the function pure-ish without coupling to the AudioContext API.
  - **Direction swap = source recreate, no offset preservation**: when
    setDirection is called mid-playback, we dispose and start a new source
    from t=0 with the other buffer. Restoring playback offset via
    `start(when, offset)` was tempting but adds complexity (AudioContext
    timeline math) and is not in PROJECT.md §3.6's spec ("swap entre les
    deux buffers"). If users complain about the audible restart, the place
    to add offset preservation is `setDirection` in player.ts — read
    `audioContext.currentTime - playStartTime` and pass to `start()`.
  - **initialDirection prop on AudioPlayer**: added now (not strictly required
    by T3 AC, but trivial and unblocks T5's GuessingPhase, which needs the
    "original" player to start in `reverse`). One ref-check on first render
    calls setDirection if non-default. Doesn't react to prop changes after
    mount — that would require a useEffect; punt until T5 actually needs it.
  - **AudioPlayer slider testing**: native `dispatchEvent` does NOT trigger
    React's synthetic onChange in jsdom because the React 19 controlled-input
    intercept reads via property descriptors that the bare `value =` assign
    bypasses. Used `fireEvent.change(input, { target: { value } })` from
    @testing-library/react instead — that one works.
  - **Recording vs AudioBuffer in the player**: only the player owns the
    "which side am I playing" state. Components above (AudioPlayer,
    AudioRecorder) don't need to know the two buffers exist beyond storing
    them. Keep this boundary as we wire the store in T4 — it should hold
    Recording, not two separate AudioBuffer fields.
  - **No coverage tool wired into the gate** (still). reverseBuffer and
    decodeRecording are 100% by inspection. If we want enforcement, T4 would
    be the moment (the gameStore tests will be the next batch claiming 100%).
  - **MIN_RATE / MAX_RATE / SNAP_RANGE** are file-local constants in
    AudioPlayer.tsx. If T4+ wants to make the range configurable per phase,
    promote them to props. For now the same constants apply to A's preview,
    B's player, and the reveal players — matches PROJECT.md §3.3.

2026-05-01 — Issue #5 (T4: State machine + phases Menu/Permission/HandoffA/RecordingA)

Wired the first half of a real round on top of the existing audio primitives.
App now boots into a Zustand-driven phase machine and walks Menu → Permission
→ HandoffA → RecordingA → Done (placeholder). All gates green: 76 tests
across 14 files, typecheck clean, oxlint clean, oxfmt --check clean, vite
build OK (PWA SW generated).

Modules delivered:
  - src/store/gameStore.ts (+ .test.ts) — single Zustand store. State shape
    `{ phase, originalRecording, guessRecording, notes }`. Phase type is
    `'menu' | 'permission' | 'permissionDenied' | 'handoffA' | 'recordingA'
    | 'done'` (the last one is a placeholder until T5 lands handoffB+). Seven
    actions: startGame, permissionGranted, permissionDenied, retryPermission,
    confirmHandoffA, finishRecordingA, backToMenu. Invalid actions in the
    wrong phase are no-ops (decision documented in this note: the phase
    component never gets to dispatch the wrong action in normal flow, and
    no-op is less disruptive than throwing for misclick edge cases). 17 tests
    covering each transition + each invalid-state no-op + two end-to-end
    walks (happy path and permission-denied retry).
  - src/phases/MenuPhase.tsx (+ .test.tsx) — heading + "Démarrer une partie"
    button → startGame.
  - src/phases/PermissionPhase.tsx (+ .test.tsx) — useEffect calls an injected
    `requestPermission` (default: `navigator.mediaDevices.getUserMedia`).
    Resolves → stops the granted stream's tracks (we only wanted the prompt;
    AudioRecorder will request its own stream when it actually records) →
    dispatches permissionGranted. Rejects → permissionDenied. Cancellation
    flag in the effect cleanup avoids dispatch-after-unmount on hot
    transitions. 2 tests cover both branches.
  - src/phases/PermissionDeniedPhase.tsx (+ .test.tsx) — alert + collapsible
    iOS/Android instructions + "Réessayer" button (retryPermission) +
    "Retour au menu" button (backToMenu). 2 tests.
  - src/phases/HandoffAPhase.tsx (+ .test.tsx) — message + "Continuer"
    button → confirmHandoffA. 1 test.
  - src/phases/RecordingAPhase.tsx (+ .test.tsx) — wraps the existing
    AudioRecorder with maxDurationMs=15000, forwarding finishRecordingA as
    onRecorded. Accepts the same injection props as AudioRecorder
    (audioContextFactory, recorderFactory, decode, reverse) so jsdom tests
    can stub everything. 1 golden-path test that records → stops → asserts
    store transitioned to `done` with `originalRecording` populated.
  - src/phases/DonePhase.tsx (+ .test.tsx) — temporary terminal screen with
    a "Retour au menu" button. Exists only to give T4 a closed loop; T5
    replaces it with HandoffB. 1 test.
  - src/App.tsx — replaces the demo page. Reads `phase` from the store and
    renders the matching phase component. Owns the lazy AudioContext via a
    ref (same pattern as before) and passes `getAudioContext` to
    RecordingAPhase. App.test.tsx updated: 3 tests covering menu render,
    handoffA render via setState, permissionDenied render via setState.

Design notes worth flagging for the next agent:

  - **Invalid-state actions are no-ops, not throws**. Implementation is
    `set((s) => s.phase === EXPECTED ? { ... } : {})`. Reasoning: the UI
    only exposes an action's button while in the corresponding phase, so
    in practice the wrong-phase path is dead. Choosing no-op over throw
    means a hot-reload, double-click, or stale-closure dispatch can't crash
    the app. If T5+ ever needs to *detect* an invalid dispatch (e.g. for
    logging), revisit — the cheapest path is to switch to throws and let
    the call sites catch.
  - **Test reset uses merge, not replace**. `useGameStore.setState({
    ...INITIAL_STATE })` (no `true` second arg). The replace mode wipes the
    action functions off the store, breaking subsequent action calls in
    the same test. This is documented in zustand but is a foot-gun on
    first encounter. INITIAL_STATE is exported for this exact use.
  - **PermissionPhase calls getUserMedia and immediately stops the tracks**.
    Why: the only goal of this phase is to surface the browser permission
    prompt. The actual recording stream is requested again by the recorder
    wrapper inside RecordingAPhase. After permission is granted, the
    second getUserMedia call resolves silently with no prompt. This avoids
    keeping a hot mic open across the HandoffA screen. Confirmed in iOS
    Safari and Chrome behavior docs; not e2e-tested (anti-goal).
  - **AudioContext is owned by App, passed as a factory**. Same pattern as
    pre-T4. RecordingAPhase takes `audioContextFactory: () => AudioContext`
    and forwards it to AudioRecorder. If T5 needs the same context in
    GuessingPhase (likely — both AudioRecorder and AudioPlayer want it),
    the right move is to extract a `useAudioContext` hook or stash it in
    the store. Don't create two contexts — most browsers cap them.
  - **Phase components dispatch via the store, not props**. They call
    `useGameStore((s) => s.action)` directly. This makes them harder to
    unit-test in isolation, but the store is itself well-tested and easy
    to seed via setState — net positive ergonomics. The same convention
    should hold for T5's HandoffB / Guessing / ConfirmEnd phases.
  - **DonePhase is throw-away**. It exists only so the T4 loop closes and
    a user doesn't get stuck. T5 (issue #6) replaces it with HandoffBPhase
    and the `done` value drops out of the Phase union. Don't add features
    here.
  - **Zustand v5 added** (`bun add zustand` → 5.0.12). PROJECT.md §4 lists
    zustand without a version; no surprise.
  - **Pre-commit gate verification skipped** in this session — I ran the
    individual scripts (typecheck/test/lint/format:check/build) but not
    `husky` itself. The hook should still fire on commit; if it fails
    because of staged-only oxfmt issues, run `bun run format` and re-stage.
